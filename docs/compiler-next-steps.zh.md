# 进行中的 QLang 编译器收尾工作

（本文件是 `docs/compiler-next-steps.md` 的中文译本。）

## 优先级与范围

优先处理 QLang 自举编译器与解释器、普通语言执行、动态模块,以及有用的源码诊断。共享的 QLang AST 是权威来源;语法糖不得要求独立的后端语义。Rust 是被保留的自举/嵌入实现。除非它阻碍 QLang 工作,否则不要改动它;把独立的差异记录在 [retained-rust-issues.md](retained-rust-issues.md)。

早先对 pow 及其他非必要 Math/库工作的推迟,在 2026-10-07 被取代:用户选择继续满足可移植标准库的需求,批准了 `Number.frexp`/`Number.ldexp` 表示机制与 `String.fromCodePoint` 机制,并把 `JSON.parse` 与 `Math.sqrt`/`pow`/`sin`/`cos` 移入普通 QLang。性能优化与内存管理替换仍被推迟;不要仅仅因为产物已经存在就重新启动那些候选。只有当库问题会阻碍编译器/自举核心或普通语言执行时,它才优先。不要处理尚未决定的 Infinity/NaN 全局名。

当前顺序:

1. 动态扩展桥:在所有六道集成门禁与自举不动点通过之后已应用。保留其已验证的语言/ABI 行为。
2. 修复函数、闭包、语句、作用域、初始化、模块执行与错误传播中的失败。验证最终源码修订。
3. 数字对象键修复:在所有六道终版门禁通过之后已应用,与推迟的 Math 迁移无关(细节见下)。
4. 在主要语言路径可靠之后,继续满足可移植标准库的需求。缺失的公开能力需要用户给出具体决定;记录下来,而不要发明后端特定的库实现。

## 需保持的语言行为

- 已声明但未初始化的绑定会建立词法作用域并遮蔽外层绑定。**读取它是前端(编译期)错误** —— 不是运行期的 Uninitialized 值:共享解析器会跑一个确定赋值检查(见下)。未声明/私有的名字不能使用。不要引入 undefined 值。保持 null 与 Null 区分。
- 内建名遵循普通的词法查找、遮蔽与捕获赋值。公开重绑定不得覆盖私有的运行期/库绑定。
- 函数元数、部分应用、注解与 Error 实参策略,在普通调用与扩展回调之间必须一致。函数内部保持隐藏;已有的 native 函数名仍然可用。
- 导入在表达式所在的作用域中执行,并在定义它的源文件处解析路径。被跳过的导入/导出不会创建绑定,也不会抹掉外层注解。导出表属于定义它的模块,并且在逃逸后仍然存活。
- 静态循环模块图是允许的;初始化执行时的重入是 ImportCycle。计算式导入使用独立编译的共享库,带 ABI 检查与全新的模块初始化。没有运行期源码编译器/JIT。
- 跨扩展的别名、循环与可变值保持同一性。候选桥在其 Interpreter 生命周期内保留同一性对;更细粒度的回收与 DSO 卸载仍未实现,不算已完成的内存工作。

模块契约见 [module-semantics.md](module-semantics.md)。

## 可移植标准库仍未完成

所有库算法都必须是两条执行路径共享的普通 QLang;LLVM 实现语言机制。QLang 源码打包同样用 QLang。Python 的测试/链接/数据生成工具不是语言实现。

String、Array、基础 Math、Number、Object 以及整个 JSON 模块(stringify 与 parse)都通过共享的 QLang 加载器安装。Number 暴露普通 QLang 的 `parseFloat`、`isNaN` 与 `isFinite`;Object 暴露普通 QLang 的 `values`、`merge`、`hasOwn`、`get` 与 `field`。String 包含已验证的 Unicode 大小写/空白数据;Array 算法使用现有的语言索引/删除操作。Math 包含 PI、E、abs、trunc、floor、ceil、round,现在还包含 sqrt、pow、sin 与 cos,它们重建于 frexp/ldexp 机制之上。`JSON.parse` 是普通 QLang,用 `String.fromCodePoint` 解码 `\uXXXX`/代理对;运行期原先的 `__jp_*`/`__json_parse` 已移除。对象键枚举仍使用现有的 native `std.Object.keys` 反射操作,所以 Object 算法已迁移,但完整的 Object 可移植性尚未完成。

Number.toString 与完整的数字格式化可移植性、对象键反射、文件系统、基于熵的 Math.random,以及可变元 Math.max/Math.min,仍需迁移/审计。`Number.toString` 是运行期内部的(`__str`、诊断、对象键强制转换),其精确最短位数路径使用裸大整数层;`Math.random` 依赖熵系统调用;而 `Math.max/min` 必须留在运行期代码中 —— 把它们的比较移入库中的尝试被调用缓冲区契约否决,该契约钉死了可变元 max/min 调用不做任何逐调用的堆工作(一旦函数体变成库调用,+1000 次调用的分配量从 6664 增至 12664),并且它们的 Error 实参消息会点名函数,而这只有分发器才能产生。不要把把特权运行期算法搬进一个新文件算作可移植性。

Unicode 码点转换(`String.fromCodePoint`)与精确的 binary64 表示(`Number.frexp`/`Number.ldexp`)现已作为获批准的机制提供。仍缺失:OS 效应、结构化 Error 构造、可变元调用、有意的 Error 实参,以及可移植的对象键枚举,此外还有库内部的一个负零符号判据(目前只有运行期的 `Number.toString` 文本可作判据)。有些算法可以使用现有算术;仅凭某个旧的裸内存依赖并不足以成为新增原语的理由。

详细审计见 [stdlib-capability-gaps.md](stdlib-capability-gaps.md)。把缺失的 QLang 能力报告给用户,并在添加公开原语之前取得设计确认。让被推迟的数字候选保持隔离。

## 表达式内部的 return 流

AST 覆盖审计发现,共享解析器在语句位置与表达式位置发出同一个 If 节点,但核心求值在表达式位置丢弃了它的 Return 流。用已核验的归一化核心做的一次完整运行在九个上下文中确认了该问题:初始化器、数组元素、调用实参、算术操作数、一元操作数、循环条件、赋值成员接收者、赋值索引接收者与赋值索引表达式。每一个都会错误地执行后续副作用;嵌套函数 return 控制则正常。进程以 0 退出,stderr 为空。实际输出保留在 `target/if-expression-return-audit/core.stdout` 与 `core.run.json`。native O0 对比现已完成,退出码 0、stderr 为空、输出与预期完全一致:全部九个表达式用例都立即返回且无后续副作用,嵌套调用控制继续正常运行。因此,引擎间的分歧是由执行确认的,而不只是源码检查。

`target/if-expression-return-fix/` 中的修复把 Return 完成态与普通值和 Error 分开携带,然后在外围边界恢复语句流。它覆盖注解、赋值接收者/索引与一元传播。Return 载体使用私有同一性令牌,所以一个名为 Return 的 Error kind,或形状类似的用户对象,都无法伪造一个。

修复已应用。最初的十行表达式观察在 native O0 与修正后的核心上通过;31 项检查的边界夹具在 native O0/O2 与修正后的核心上通过。三道完整门禁全部通过:解释器核心、运行期诊断与扩展桥,各自以 0 退出并带其确切成功标记。最终应用记录了相对 Object 基线的七个改动文件;合并后的 main 快照有 216 个输入。证据在 `target/if-expression-return-fix/`,尤其是 `verify-full.results.json` 与 `main-application.json`。编译器源码/AST/运行期未变;自举证据继承自已核验的 Object 应用。这修复了函数局部的 Return 流。单独的函数作用域规则现由共享解析器实现,如下所述。

## 仅在函数内允许 return 已实现

用户批准的规则由 `bootstrapped/parser.ql` 强制执行:`return` 只在词法函数体内有效。脚本与模块顶层的 return 是语法错误,包括位于未执行分支中的那些。插值继承外围函数上下文;参数注解保留在定义的外层上下文中。嵌套函数在解析完其函数体时恢复该上下文。模块源码在编译器生成的工厂函数把它包裹起来之前就被检查。

## 确定赋值:读取未初始化值是编译错误(2026-10-09)

用户选择改变语义:绑定在被读取之前必须已初始化,违反这一点是前端错误,而不是运行期的 Uninitialized 值。实现位于共享解析器(`bootstrapped/parser.ql`),因此自举编译器、boot 解释器与 native 解释器都会得到它。

规则:`let x;` 声明一个未初始化绑定;赋值会初始化它;`if`/`else` 汇合在活跃路径上是合取的(单边分支不构成初始化);循环体内的赋值永远不会变为确定;`return` 终止可达性。读取一个未被确定初始化的绑定会产生 `reading uninitialized variable: NAME`,并带原始源码坐标。

可靠的逃生口:任何出现在嵌套函数内部的名称都被豁免(对捕获的过近似)。那些读取被推迟了 —— 闭包可能在赋值之后读取外层绑定 —— 因此生成端为它们保留运行期检查。语料依赖这一点:runtime.ql 与 qlangc.ql 在函数体内有前向引用。

效果:在同函数体内读取得到保证之后,生成端不再为它们发出 null 检查、`ql_empty` 检查或其冷诊断路径(`aot/qlangc.ql`,depth 0 与非可选作用域)。一个 `x = x + 1` 从 301 行 IR 降到 174 行,发出的 IR 缩小约 34%(1000 条语句 33.9 → 24.5 MB,3000 条语句 62.2 → 40.9 MB),编译器的静态字符串声明数从 2699 降到 2086。仅用 native 编译器自举验证(`stage1 --emit-llvm aot/qlangc.ql aot/runtime.ql`,41 s),stage2/stage3 IR 逐字节一致,且 native 编译器拒绝 `let x; x;`。

流程说明(用户指示):用 QLang 编译出的 native 编译器来构建和测试,而不是用 Rust 宿主。`stage1 --emit-llvm aot/qlangc.ql aot/runtime.ql` 约 41 s,而 Rust boot 路径要约 13 min,并且它演练的是最终发布路径。

那些刻意演练旧运行期语义的夹具被改写(t13/t15/t20/t21/t22/t23/t33/t34/t38);它们的覆盖迁移到前端诊断夹具。`tests/uninitialized.rs` 运行被保留的 Rust 宿主,后者仍报告运行期值 —— 这是 [retained-rust-issues.md](retained-rust-issues.md) 中记录的一处差异。

扩展(同一天):

- 同一趟还会跟踪一个静态已知的局部函数的元数(在重新赋值时刷新,跨分支保守合并),因此用**多于**其声明数的实参调用它是前端错误(`Arity mismatch: expected N arguments, got M`)。更少的实参仍然合法(部分应用),成员/未知被调者保留运行期检查,像 `Math.max` 这样的可变元运行期 native 不受影响。t12 的实参过多用例迁移到诊断夹具(现在 36 个非法用例)。
- 生成端:不带类型注解声明的绑定会存储零类型/零文本,因此重新赋值时的 `__check_binding` 菱形总走它的普通分支。`emitLetStmt` 把带注解的绑定记录进 `curScope.annotated`,`emitStoreByName` 对其余的发出普通存储。一个 `x = x + 1` 从 174 行 IR 降到 108 行,1000 条语句从 24.5 MB 降到 21.0 MB。
- 前端能证明的常量失败也算错误:除以或模以字面量零(`division by zero`),以及整数字面量索引越出数组字面量范围(`index out of range: N`,正负皆然)。`&&`/`||` 的右操作数处处豁免,因为它可能永远不会被求值 —— `false && 1 / 0` 仍然合法,并被钉为合法用例。另外两个候选被刻意*不*添加:对标量字面量做成员访问(字符串字面量确实有成员 —— `"ab".length` 为真 —— 所以那些表属于运行期,而不是前端的镜像)以及与其注解相矛盾的字面量初始化器(注解是任意表达式,在运行期求值;静态判定它需要前端并不具备的类型值概念)。那些用 `1 / 0` 来*获取*运行期错误值的夹具现在改为除以一个变量零,以保留它们的源码位置断言(t38、t40、native_source_bridge、t6、v1_shortcircuit)。

## 语句以 `;` 结束(2026-10-09)

在推演过一套行首/行尾续行方案之后定下:**语句只在 `;` 处结束**(或在块状语句的 `}` 处结束)。换行永远不会结束一条语句,所以解析是贪婪的,每份源码都只有唯一一种解析 —— 不再留有需要解决的续行歧义。针对该歧义的早期实验(拒绝无副作用的表达式语句,以及首 token 既能续上一行又能开始一条语句的语句,即 `-`、`+`、`(`、`[`)作为不必要的复杂度被回退。

- 每条产生值的语句都需要 `;`:声明、赋值、`return`、`export`,以及任何表达式语句 —— **除了块的尾语句,在那里 `;` 可以省略(像 Rust 那样)也可以写上;两者含义相同。** 操作层面的规则是:缺少 `;` 就是错误,除非下一个有效 token 是 `}` 或输入结束。缺失的 `;` 会在出错的 token 处报告(`expected ';' after declaration` / `after statement` / `after return` / `after export`)。
- `if`、`while` 与裸块在它们的 `}` 处结束;其后的 `;` 是一条空语句,这就是 `if c { … };` 仍然合法的原因。
- 独立的表达式语句是合法的(`xxx;`、`xxx.yyy[zzz];`、`[1, 2];`),正是它让一条链可以跨到后续行继续。在此规则之前,`let a = 1 let b = 2;` 与 `{ x y }` 会被悄悄接受(语句之间没有分隔符),而这正是它补上的漏洞。
- 语料本身已经以 `;` 结尾,所以该规则不带来任何源码改动。同一次会话中还保留了:确定赋值、静态元数检查、字面量除零,以及字面量数组索引边界。

## 换行符:保持 core.autocrlf 关闭(2026-10-09)

这个检出曾设置 `core.autocrlf=true`,因此一次 `git checkout` 把源码改写成了 CRLF。库捆绑嵌的是模块*字符* —— 它的换行在生成的字符串字面量内部被转义 —— 所以 CRLF 工作区会让 `stdlib/build_bundle.ql --check` 报告捆绑过期,即使已提交的捆绑是正确的,而且它会悄悄改变编译器解析的源文本(位置与内嵌字面量)。修复:`git config core.autocrlf false`,然后从索引重新落出工作文件(`git checkout-index -f -a`,或从 `git cat-file blob :<path>` 复制每个 `git ls-files` 条目),之后 `--check` 就能通过。夹具仍可刻意使用 CRLF —— 打包器测试覆盖混合换行 —— 只有喂给捆绑的源码需要 LF。

## 编译器生成规模:量测与一项修复(2026-10-08)

用户取消了对编译器可扩展性工作的推迟。干净的测量(用 native `stage1`,不跑其他任何东西):一个平凡程序在 14.4 s 内发出 20.0 MB;再加 1000/2000/3000 条 `x = x + 1` 语句,耗时 45.1/127.7/252.1 s,产出 34.6/49.2/63.8 MB —— 基线下为 0.72 s/MB,升到约 5.7 s/MB。增长跟随的是累积的*已发出字节数*,而非语句数:一个 4000 条语句、绑定互不相同的程序几乎不发出 IR,并保持线性(约 1.8 ms/语句)。

通过直接测量排除的因素:数组追加(120 万元素,线性)、字符串拼接 + 存储(240 万个存活字符串,线性)、`println`(约 3 µs/行),以及 GC 频率(把回收阈值提高 16× 在 n=1000 时只带来约 20% 的收益,并在 n=2000 时 OOM)。平凡程序的峰值 RSS 是 208 MB,n=1000 时是 574 MB —— 堆每发出 1 行就增长约 500 B,约为保留的 IR 字节约 10× —— 所以剩余的逐行成本增长与把整个 IR 都持在内存中带来的内存/GC 压力一致:主函数体、每个函数块以及每条字符串声明都会被缓冲,直到最后的 flush。

已修复:`aot/qlangc.ql` 中的 `escapeBytes` 以前逐字节用 `text = text + …` 构建转义字面量 —— 每个字面量 O(len²) —— 现在改用 O(n log n) 的成对拼接,并带小输入快速路径。发出的 IR 不变,自举门禁 47/47 通过,字面量密集的编译提升约 11%(一个 3000×1000 字符字面量的程序 39.6 → 35.1 s;解释器的 `run_file.ql` 约 40.6 → 35.9 s)。

下一步(结构性,尚未尝试):让 main 的函数体流式发出而不是缓冲,办法是先用已算出的绑定集合确定 main 的帧大小,从而在函数体发出之前就已知它的栈上 allocas。这会移除当前设计强制产生的大存活集;它需要自己的前后对比测量与完整门禁。本沙箱没有 `perf`/`gdb`,所以更细的剖析需要要么一个临时的 clock 叶子函数,要么一台启用了 profiler 的机器。

通过在 `qlangc.ql` 中临时加入 `/proc/self/stat` CPU 时间戳插桩得到的阶段分解(`/proc/uptime` 在本沙箱中是冻结的),单位为 CPU 秒:

| 阶段 | n=0 | n=1000 | n=2000 | n=3000 |
| --- | --- | --- | --- | --- |
| 前端(词法+解析 用户+库+运行期) | 4.17 | 5.36 | 6.77 | 8.12 |
| 发出运行期 | 1.54 | 1.53 | 1.56 | 1.54 |
| 发出库 | 3.44 | 3.44 | 3.43 | 3.42 |
| **发出用户程序** | **0.00** | **20.34** | **76.23** | **167.72** |
| flush | 1.00 | 1.79 | 2.42 | 3.42 |
| 合计 | 10.2 | 32.5 | 90.4 | 184.3 |

所以固定成本不大且实打实 —— 整个运行期+库的发出约 5 s,前端 4–8 s —— 而**发出用户程序占约 90% 的时间,并且是二次的**(每条语句 20 → 38 → 56 ms,每发出 1 行约 65 → 180 µs)。flush 很便宜(最多 136 万行只需 1–3.4 s),所以 I/O 不是问题。还剩两根杠杆:每次操作发出更少的 IR 行(一个普通的 `x = x + 1` 目前发出约 311 行 —— 输出更少意味着生成端工作更少、内存更少、二进制更小),以及不再把整个 IR 持在内存中。插桩在测量后已回退;唯一保留的编译器改动是上面的 `escapeBytes` 修复。

对一条 `x = x + 1` 所增加的约 311 行做解剖(`stage1`,把 `let x = 1; println(x);` 的 IR 与同一程序加上该赋值后的 IR 做 diff):126 个 `getelementptr`、84 个 `load`、约 100 个 `store`、29 个 `call`、29 个基本块、18 个 `extractvalue`、17 个 `alloca`、16 个 `inttoptr`、13 个 `icmp`、9 个 `phi`。热路径代码很小 —— `+` 被内联为 `ql_tag` 检查加 `fadd` —— 所以体量来自:

- **在每个位置内联发出的冷错误路径。** 每次标识符*读取*都会发出一个 "Uninitialized" 检查加上它的错误构造/传播块;每次写入都会发出一个绑定缺失(`UndefinedVariable`)路径和一个 `__check_binding` 注解菱形;每次调用后面都跟着一个内联传播块。每个约 40–80 行,其中大部分是从不在正常路径上执行的诊断块。
- **每个调用点一个被提升的 `alloca`**(就这一条语句就有 17 个),来自入口块栈槽机制,所以一个 3000 条语句的模块会提升出数万个 allocas。

找到并修复了根因(分支 `emission-scaling`):`String.join` 以前逐元素用 `out = out + …` 构建结果 —— O(n²) —— 而 `stackEntry()` 会 join 逐调用点的栈槽列表,该列表随每条语句增长。两项修复:

- `stdlib/string.ql` 中的 `String.join` 现在使用成对归约(O(n log n));这是根因修复,保护每一个 join 调用方。
- 调用实参缓冲区按大小池化(`aot/qlangc.ql` 中的 `argSlot`),而不是每个调用点一个 `alloca`,所以 main 的入口块只持有少数几个 allocas,而不是数万个。这是安全的,因为调用 ABI 只借用缓冲区(部分应用会复制),每个实参都在存储之前被求值,且每次使用都被 `lifetime.start/end` 括起来。

生成耗时(用 native `stage1`,不跑其他任何东西):

| case | before | after |
| --- | --- | --- |
| trivial `println(1)` | 14.4 s | **10.1 s** |
| +1000 `x = x + 1` | 43.5 s | **13.6 s** (3.2×) |
| +2000 | 127.7 s | **17.2 s** (7.4×) |
| +3000 | 252.1 s | **34.8 s** (7.2×) |
| interpreter `run_file.ql` | 35.9 s | **30.0 s** |
| t16 fixture | 12.1 s | **9.5 s** |

仅池化一项就贡献了约 2.4×(它缩小了被 join 的列表)。已验证:自举门禁 47/47,包括 stage2/stage3 IR 不动点;解释器 52/52;数字套件;调用缓冲区分配仍为平坦的 `[633, 633]`;生命周期套件;扩展与扩展桥套件;可移植 String 套件;`cargo test`。

剩余部分:逐语句的 IR 体量仍然是那些在每次读取、写入和调用处内联发出的冷错误/诊断路径(每个约 40–80 行,从不在正常路径上执行)。把它们共享起来 —— 按错误*形状*(kind + message)每个一个辅助函数,以源码位置为参数 —— 应能把 `x = x + 1` 从约 311 行降到大约 40 行,并进一步削减生成耗时与产物大小;它需要保留确切的错误 kind/message/位置,外加完整门禁。另外已知是二次的:`stdlib/json.ql` 中的 `JSON.stringify` 逐 token 用 `output = output + …` 构建输出,所以大值要付 O(output²)。两者均尚未尝试。

## 扩展套件需要一个允许 dlopen 的 TMPDIR(2026-10-08)

`aot/run_extension_tests.py` 与 `aot/run_extension_bridge_tests.py` 会在一个临时目录里构建宿主二进制与 DSOs,然后 `dlopen` 它们。在本沙箱中,动态链接器命名空间只允许 `/data`(加上系统路径),所以在默认 `TMPDIR`(`/tmp`)下每个插件都加载失败,套件报告扩展失败("library ... is not accessible for the namespace")。以 `TMPDIR=/data/qltmp python3 ...` 方式运行就让两者都通过 —— 扩展套件是 `ALL CHECKS PASS`,桥套件是 `Native core extension suite: ALL CHECKS PASS`。这是环境限制,不是产品缺陷;同样的失败在改动前的编译器上也会出现,与任何迁移都无关。

## 冷路径分离:已在分支 `cold-paths-and-lazy-std` 完成(2026-10-09)

逐读取者的带位置错误路径(带源码坐标的 `__err_at`)现在**每个模块只发出一次**,作为一个私有函数 `@__cold_located_error`,使用普通 ABI(值走寄存器,无帧缓冲区),而不是在每个读取者处内联。测量结果:

- 一次读取:60 -> 37 行 IR;`x = x + 1`:111 -> 66
- 整个模块(空程序,即运行期与标准库):339,948 -> 257,043 行,15.84 MB -> 12.10 MB(-24 %)

已验证:自举门禁 47/47(包括 stage2/stage3 不动点),native 解释器 53/53,以及运行期诊断与源码上下文套件 —— 后两者钉住了错误坐标与踪迹,所以这次分离是保行为的。

这套工具链施加的两个约束,都是硬碰硬踩出来的:

- **对同一模块中定义的函数做前向 `declare` 会被拒绝**("invalid redefinition",用普通 `i32` 即可复现)。这就是为什么运行期调用全部经由闭包盒间接进行。因此该辅助函数不能提前声明:它在编译结束时生成(那时模块绑定已存在),并被**接进输出流中紧跟 prelude 之后的位置**,位于每次使用之前。
- **该辅助函数必须直接对运行期帧做索引。** 一个运行期名字的查找深度是 `curScope` 到 `runtimeScope` 的编译期距离,因此该辅助函数把自己的作用域设为 `runtimeScope`(相对其参数深度为 0),而每个调用点传入的运行期帧,是通过每层走一次 `curEnv` 的父链得到的。

该分支的下一步:(c) 对运行期函数的直接调用(这需要函数定义在 `main` *之前*发出,因为此 clang 禁止前向声明),然后是按需求的 `std`。注意链接期垃圾回收对标准库帮不上忙:启动时构建的 std 命名空间对象引用了每个成员,所以 `opt -passes=globaldce` 在 278 个函数中移除 0 个。按需求的 std 必须是*编译器*的决定(只发出被引用的成员,传递闭包,遇到动态访问时回退到全部发出)。

### (c) 有选择的直接运行期调用:已完成

一个函数体已经发出的运行期函数,现在会被直接调用(`call %ql_value @ql_fnN(...)`):代码地址已知,所以盒的代码指针加载与间接分支都消失了。帧与闭包仍来自盒,实参仍走池化缓冲区,所以 ABI 不变。安全性依据两个事实:此工具链要求定义先于直接调用,且运行期绑定是私有的、从不重新赋值 —— 已检查,运行期的 173 个顶层绑定中只有 4 个可变状态名曾被赋值,且它们都不是函数。

为使其合法,模块布局现在是 prelude → 冷辅助函数 → 函数体 → main(全局量最后;它们无序)。闭包盒让该顺序对每次间接调用都无关紧要。

测量结果:整个模块中有 4850 次直接调用对 411 次间接调用;模块从 257,043 行降到 247,343 行(12.10 MB 到 11.68 MB);一次读取从 37 行降到 35 行,`x = x + 1` 从 66 行降到 64 行。编译器本身快 3-5%(q1000 15.43 -> 14.99 s,p3000 21.48 -> 20.36 s)。

## 生成路线图(2026-10-10)

HEAD 上一条 `x = x + 1` 的实测构成(每条语句约 62 行 IR;带位置错误辅助函数自身的函数体则是每模块另加约 30 行的一次性开销):

| part | lines | why |
|---|---|---|
| read `x` | ~15 | frame load of the binding, the "is this value an Error?" test (ql_tag/icmp/br), its cold branch and phi, frame pointer load |
| `+` dispatch | ~30 | the "are both operands Numbers?" test, the inline numeric fast path (extractvalue/bitcast/fadd/insertvalue), and the general path (frame-slot lookup of the operator, argument buffer, direct call to the runtime's `__op_add`) |
| write `x = ...` | ~10 | another Error test with its cold branch and phi, the binding store, and the statement-value bookkeeping store |
| diagnostic file-name string | 2 | interned once per module |

杠杆,大致按价值排序:

1. **按需求的标准库** —— 发出的模块中 68% 是库(含它是 247,351 行,不含是 79,684 行,而那个程序一点也没用到它)。在编译器侧对库的顶层绑定以及暴露它们的对象字面量做可达性分析,并在程序对 `std` 的使用无法静态枚举时回退到全部发出(模块对象逃逸进变量、动态键、未知成员名 —— 注意 `std.Number.toString` 及其同类来自*运行期*,而不是库,所以它们不算"未知")。必须用 `std.*` 夹具验证;错误的决定会在运行期失败,而不是编译期。
2. **在常量和同作用域绑定上折叠 `@ql_tag`** —— 读/写 Error 测试在每个位置各花约 3 行;对一个编译器知道绝不可能是 Error 的值(一个字面量,或一个其所有赋值都是字面量的绑定),该测试及其冷分支就是死代码。
3. **把运行期盒加载提取公共子表达式** —— 每个操作符/调用点都会从同一个模块帧重新加载被调者的帧指针与闭包(每处 5-8 行);一个按函数的 CSE 或从循环中提升会消掉大部分。
4. **在无人观察时去掉语句值记账** —— 每条语句都把一个新值存进语句槽;当没有任何东西读取块的值时,一整块都是死代码。
5. **把数字测试与分发合并** —— 内联的 "都是 Number 吗?" 测试重复了运行期 `__op_add` 本来就做的检查;无条件调用运行期路径会缩小各位置,代价是一些运行期开销。

### 操作符路径:它的约 47 行花在哪里,以及一些想法

| piece | lines |
|---|---|
| "are both operands Numbers?" test | 5 (`ql_tag` x2, `icmp` x2, `and`) |
| inline numeric fast path | 9 (extractvalue x2, bitcast x2, `fadd`, bitcast, insertvalue x2) |
| general path: fetch the operator's frame/closure | 9 |
| general path: argument buffer and call | 7 |
| branches and phi merge | ~5 |

`aot/value_abi.ql` 是一段手写的 `alwaysinline` IR 叶子(`ql_tag`、`ql_empty`、`ql_word`、`ql_truthy`)块,编译器整块发出,所以把热片段搬进一个叶子不需要任何 ABI 或链接器改动。

1. **把帧/闭包取值提升到函数作用域(收益最大)。** 那 9 行在一个函数的每个调用点都相同,因为一个运行期函数的盒是单例,且运行期绑定从不重新赋值(与直接调用改动所依赖的是同一条不变量)。在入口块加载一次,然后引用寄存器:每处省下约 8 行。该模块约有 4,850 次直接调用,所以这大约值 35k 行,约占模块的 14%。这些加载必须放在入口块,而不是首次使用处,否则循环之后的使用就不会被支配。
2. **一个 `ql_both_number(a, b)` 叶子**取代类型测试:5 行 -> 2。
3. **为数字快速路径做叶子**(`ql_num_add` 及其同类,`alwaysinline`):9 行 -> 1。`-O2` 会把它们内联回去,所以运行期不变,只有 IR 体量缩小(`-O0` 构建则要付一次调用)。
4. **给 `/` 与 `%` 一条快速路径。** 它们今天跳过了双字面量快速路径,所以花 82 与 99 行。有了 `ql_num_div` / `ql_num_mod` 叶子(含零检查)后,它们降到 `+` 的形状:每个省 50-60 行。这一族里单笔最大的收益。
5. **折叠读/写 Error 测试**(3 行加分支与 phi),当该值不可能是 Error 时:一个字面量,或一个其赋值全是字面量的同作用域绑定。
6. **161 行的 `&&`** 是两个操作符加短路机制;一旦操作符缩小,它会降到大约 90。
7. **长期:带解箱局部变量的类型推断。** 如果一个绑定或参数可证明是 Number(或 String),就让它保持解箱,于是每个标签测试、快速路径与 pack/unpack 都消失:一个操作符变成约 2 行,一次读取约 2 行。这是对 "为什么一个赋值需要这么多指令" 的结构性回答;代价是一次真正的推断过程。

不要分离通用(非数字)路径:它不冷 —— 字符串拼接就走它 —— 所以把它拆到行外会让字符串密集的代码变慢。

### 真正的成本不是检查,而是不知道类型(实测)

同一条语句,只在于编译器是否知道操作数类型上不同:

| statement | lines |
|---|---|
| `z = 1 + 2;` (literals: the compiler emits the numeric path alone) | **21** |
| `z = y + 1;` (dynamic) | **62** |
| `z = y + y;` (both dynamic) | **75** |
| `z = s + s;` (strings, general path) | **75** |
| `y;` / `z = 1;` | 13 / 2 |

所以一条语句成本的三分之二是*编译期不知道类型*的代价,而且它并非花在那 5 行测试上:它花在不得不**同时**发出专用数字路径(9 行)与通用分发路径(16 行),再加上汇合它们的分支。测试很便宜;真正花掉 40 行的是其结果未知这一事实。

这重排了路线图。机械性的想法(叶子、提升帧取值、给 `/` 与 `%` 一条快速路径)只能回收机制开销,每个操作符约 15-20 行;它们无法消除重复的路径。只有知道类型才能,而对一条操作数被证明为 Number 的语句,实测目标是 62 -> ~20。

狭窄的第一步:**函数内类型推断**,限定于那些初值是某一类型字面量、且从不被赋其他类型的绑定(并且只与那个类型结合)。它与确定赋值趟已经执行的前向流分析相同,不需要任何跨过程工作,并且每当无法证明类型时就回退到今天的动态生成。参数与返回值(每个调用点就某类型达成一致)是后面一步。

### 两层,而第二层是表示(实测)

`z = 1;`(写入一个字面量)花费 **2 行**;`z = 1 + 2;`(类型同样已知,但值是*算出来*的)花费 **21**。差别在于:

- 约 9 行装箱/解箱:操作数是装箱的 `%ql_value`,所以编译器为一次加法就要解箱(extractvalue、bitcast)、计算(`fadd`)并重新装箱(bitcast、insertvalue);
- 约 7 行 "这个值是不是 Error?" 测试加上它的分支与 phi;
- 其余是语句记账。

注意 `z = 1;` 只要 2:写入的 Error 测试对字面量*已经*被跳过,所以机制是存在的 —— 它只需要知道一个算出来的 Number 也不可能是 Error。

所以成本分成两层,它们共享一个前提:

1. **编译期类型未知**迫使同时发出专用路径与通用路径,外加汇合它们的分支(同一条语句 62 对 21)。
2. **装箱的、可能为 Error 的表示**在每次计算与每次使用处都收取解箱/装箱与一次 Error 测试,并且不会仅因为类型已知就消失(计算值对字面量值 21 对 2)。

对第二层的修复,全部由与第一层相同的那种分析解锁:

- **解箱局部变量**:一个被证明持有 Number 的绑定保持为 `double`;一个 `+` 变成一个 `fadd`,没有 Error 测试(a double 不可能是 Error),没有记账 —— 一次赋值降到约 3-5 行;
- 对字面量操作数做**常量折叠**(`1 + 2` -> `3`):需要*零*分析,可以立刻做,即在已经特判两个字面量操作数的那个分支里折叠;
- 当值不可观察时,去掉语句值记账。

全部做完后,一条 `x = x + 1` 应该是 3-5 行,而不是 62。

### 类型系统是编译器应当使用的通道

QLang 的类型信息(`let x: Number = …`、`(n: Number) -> …`)在运行期强制执行,所以编译器可以*信任*它 —— 注解过的代码不需要推断过程。它确切能换来什么:

- `x: Number` 意味着 x 是**一个 Number,或检查失败时存下的 TypeCheck Error**。这足以对 x 的每次使用**去掉通用分发路径**:操作符族里单笔最大的节省(每个操作符约 16 行),而类型测试也坍缩为仅剩 Error 测试。
- 它本身并**不**允许解箱,因为 Error 状态必须保持可表示。解箱需要该检查被*证明*不可能失败 —— 右侧是个字面量,或是一个同类型的绑定。那时带类型的绑定可以保持为普通 `double`,装箱/解箱加上 Error 测试都消失:整个第二层。
- 结构化注解(`Array(Number)`、`Object({a: Number})`)可以进一步特化索引与成员访问。
- 识别注解是一次作用域感知的匹配:注解表达式是一个标识符,它解析到内建的 `Number` 绑定(而不是被遮蔽的那个)。

缺口在于:注解只对有注解的代码有帮助,而 `aot/runtime.ql` 加上标准库 —— 占发出模块的 68% —— 基本上没有注解。这一大块要么需要推断,要么需要往库源码里加注解,而后者是语言层面的决定,不是编译器层面的。

分阶段计划:(1) 常量折叠(完全不需要分析);(2) 注解驱动的特化,包括在检查可证明不会失败时省去运行期检查并解箱;(3) 为未注解的大块做推断,或者在库里加注解。按测量预期:一个 `Number` 类型的 `x + 1` 约 60 -> 14 行,一旦解箱约 2 行。

### 带类型绑定不得持有 Error(设计决定,需要批准)

今天,失败的注解检查会把 TypeCheck Error *存进*绑定,所以 `x: Number` 实际意味着 "Number 或 Error" —— 即 `T or null` 陷阱,声明类型是个谎言,每个消费者都必须处理那个额外状态。来自用户的要求:带类型的绑定恰好持有它的类型,别的什么都不持有。

最小改动,不重写错误模型:让检查在失败时**传播**,而不是存下值。QLang 已经有这条路径 —— `?` 传播(`emitPropagateError`:存进返回槽并分支到尾声,或在顶层用 `__exit_error`),与 `Error.raise` 所用的是同一条。所以这是一个语义决定,不是架构改动。

一旦 `x: Number` 真的只是一个 Number,它能换来什么:

| today | after |
|---|---|
| general dispatch path, ~16 lines per operator | removed |
| read/write Error test, ~7 lines | removed (a Number cannot be an Error) |
| box/unbox, ~9 lines | removed (the binding can be a plain `double`) |

实测目标:一个 `Number` 类型的 `x + 1` 从约 60 行降到约 2-3 行,且不需要推断过程 —— 这些信息由作者声明、由运行期强制执行。

实打实的代价:

- 这是一次**语义变更**:错误在声明/赋值处浮出,而不是在首次使用时。那些检查已存储的失败检查值的夹具(`t13` 的 `mismatch.type` / `.cause`、`t33`)必须改变,与未初始化读取和元数变更是同一种代价。
- 只有注解过的代码受益;运行期与标准库(占发出模块的 68%)没有注解,仍需要推断或添加注解。

刻意*不*提议:把整个语言从"错误即值"搬到"错误即控制流"。上面的最小版本给编译器它需要的保证,同时不动模型的其余部分。

### 参照:"自动错误传染"是什么

QLang 当前的错误语义:一个 Error 是一个*值*,而**使用它就会让它成为那次使用的结果**。`let a = 1 / 0; let b = a + 1;` 不做加法,也不抛 TypeError —— 错误感染了结果,所以 `b` 就是同一个 Error。`"a" + (1 / 0)` 不是拼接;x 是 Error 时 `x.field` 也不是 UndefinedField。编译器在每次读取、写入、成员访问、索引与操作符结果处插入 "这个值是不是 Error(tag 8)?";当是时,该值成为附带当前源码位置的结果,所以一个错误**在行进中收集位置和一条踪迹**(源码上下文与 t40 诊断所依赖的就是这个)。

与其他模型相比:Rust/Go 显式返回错误(`Result` / `(T, error)` 加 `?`);Java 的 `T or null` 把这种可能性泄漏进类型;JS/Python 展开(unwind)。QLang 是值加传染加显式 `?` —— 不展开,而且错误保持可检查(`e.type`、`.cause`、`.trace`)。

它能换来什么:被调者内部的失败无需在每一层都写 `?` 就能到达用户,它们保持可检查,而且没有展开。它的代价(实测):每次读/写/索引处的检查(占发出模块的 19.5%),以及更重要的是 "任何值都可能是 Error" 作为一条*前提*,正是这条前提挡住了类型特化与解箱。

第 1 步(已批准)正是:**传染不适用于带类型的东西** —— 失败的注解检查会传播(`?` 路径)而不是被存下,所以一个 `Number` 注解的绑定永远只是一个 Number。联合类型于是只存在于函数边界处,在那里它是合法的(一个类 `Result` 的契约),而错误仍以值的形式到达调用方。未注解的代码保持传染不变。

### Rust 式错误:契合度不错,但杠杆是关掉传染

Rust 模型的本质是两点:失败随返回值传递(带内),并且传播是显式的(`?`)。QLang 已经有了一半 —— 错误是值,`?` 恰好以那个形状存在(存进返回槽,分支到尾声),并且错误通过 `.type` / `.cause` / `.trace` 保持可检查。

真正的缺陷在于,"可能失败"目前*是每个类型隐藏的另一半*:任何值都可能是 Error,所以每次读/写都要付一次检查(实测占发出模块的 19.5%),而 `x: Number` 可能持有一个 Error。一个 Rust 式模型让 Error **成为它自己的一个类型**:一个值要么是一个 `T`,要么是一个 `Result`/Error,没有隐藏状态。

有两点要说清楚:

1. 只添加 `Result` 不会缩小任何东西。节省来自**移除传染**(那 19.5%,加上挡住特化与解箱的 "任何值都可能是 Error" 前提)。`Result` 的作用是让移除它变得符合人体工学并且*带类型*:没有它,编译器就无法知道一次调用可能失败。
2. 代价在调用点处以及库内部:每次可能失败的用法都需要 `?`,错误不再那么宽容(`let a = 1/0; a + 1` 会变成一次真正的加法,然后是一个 TypeMismatch,而不是传播那个除法错误),而 `stdlib/*.ql` 通篇依赖传染,所以需要通篇加上 `?` —— 机械但约 4700 行,而且都在热路径上。一个 `Result` 包装器还可能产生分配,除非编译器能把它保持解箱,所以它的表示必须与注解驱动的特化一起设计,而不是事后补。

建议顺序:(1) 关掉传染,让只有 `?` 传播 —— 仅这一项就能拿下那 19.5% 与诚实类型的前提;(2) 添加用 QLang 写的 `std.Result`,作为可失败调用的带类型形状,由编译器以识别 `Number` 的同一方式识别(一次作用域感知的名字匹配,不做库特判);(3) 注解驱动的特化与解箱,已批准的第 1 步是它的前提;(4) 把库的内部迁移到 `?` —— 这会编辑 stdlib 源码,所以需要先获批准。

### 实测:关掉传染要付什么代价(迁移清单)

实验:把 `emitLocatedError` 变成 no-op(关掉传染)并跑套件。体量,和之前一样:一个模块从 247,351 行降到 199,072 行(-19.5 %)。

行为:坏掉的是那些对位置敏感的套件,它们坏掉是因为带位置错误机制**就是**位置附加机制:

- `t38_runtime_diagnostics`:8 项检查失败 —— 除法坐标、调用/递归/起因的起源、"trace unavailable without changing Error"。
- `t40_diagnostic_context`:5 项检查失败 —— native 边界起源、上下文恢复、无上下文泄漏、部分 native 源码。

所以移除传染不只是 "删掉检查":错误位置与踪迹必须附到别处 —— 逻辑上附到**创建**位置(编译器发出的那些操作:操作符、成员访问、索引、调用),在那里编译器知道源码位置并能把它传进去,而不是附在每次*使用*处。这就是第 2 步需要的设计零件,也正是那 19.5% 换回来的东西。

在做第 1 步时还硬碰硬学到的:

- 早先一次被截断的 `grep | head` 引出了 "只有 t13 有注解" 的错误说法;实际有 **21 个文件**带注解(包括 `bootstrapped/parser.ql` 与 `interpreter.ql`)。大多数是能通过的注解,不受影响,但那些注解失败的夹具不然:`t38` 不得不重构(那个失败的声明现在放在一个 lambda 里,传播出来的错误通过它的结果来断言),而 `t13_bindings.ql` —— 未登记、183 行、33 条注解 —— 仍需要同样的处理。
- 从注解检查中移除 `__err_at` 包装同时也移除了错误上的源码位置;保留它并在之后传播才是正确的形状。
- 这类错误报告的列号以声明处 `let` 关键字为基准、从 1 开始。

## 待重审的设计条目:把 Error 作为调用实参传入(2026-10-10)

`__call_borrowed`(aot/runtime.ql,普通调用路径)显式拒绝模式不是 1/3/5 的 Error 实参(并且除非调用方是内部的且被豁免):

```qlang
if __isError(v) { return __err_new("TypeMismatch", "attempt to pass error value as argument", v); }
```

所以 `let f = (v) -> 42; f(e)` 中 `e` 是 Error 时,会产出一个*新的* TypeMismatch 错误,而不是 `e` 本身。这是一条刻意的规则,不是传染的残留 —— 但在 "错误是值,`?` 是唯一的传播方式" 这一模型下,它值得重审:把 Error 作为值传入也许干脆可以允许,把决定权留给被调者(它可以用 `isError`/`.type` 检查,或用 `?` 传播)。记在这里供用户决定;内部的 `exempt` 路径已经表明机制可以绕过它。

## 待日后研究的缺口:运行期提供的 std 成员没有接口类型(2026-10-10)

编译期阶段现在可以透过 `if` 的尾值和带注解的参数推导出返回类型,所以标准库自己的大多数函数都带类型了。它无法跨进*运行期*提供的那些成员:`std.Number.frexp`/`ldexp`、`Math.random`,以及用 native 实现的 String/Object/Array 成员。该阶段能读到的任何东西都没有声明它们的签名,所以任何尾部落在这类成员上的库函数都保持未知 —— `Math.sqrt` 就是例子,因为 `scaleByPowerOfTwo` 结束于 `std.Number.ldexp`。

修复办法是把那些签名用语言写下来,作为一张编译器读取的小型接口表(stdlib 侧,契合 "运行期提供机制,语言声明接口")。刻意推迟;它只影响尾部落于运行期成员的那少数函数。

在 stdlib/math.ql 中加入参数注解再加上 if 尾汇合之后的实测(相同源码、相同输出):
  `std.Math.sqrt(x) + 1`   216946 -> 216846 lines  (-100)
  `std.Math.abs(x) + 1`    216937 -> 216837 lines  (-100)

## 待办(最后做):把 stdlib 源码生成器从 Python 移走

真正重要的那条链已经是纯 QLang:`stdlib/*.ql` -> `build_bundle.ql`(QLang,任何地方都没有 exec/spawn)-> 编译器解析的内嵌 `standardLibrarySource` 字符串。Python 只出现在边缘:

  - `stdlib/generate_unicode_tables.py`、`aot/generate_math_constants.py`:源码生成器,其输出(QLang)已提交,所以构建从不运行它们 —— 只有刷新表的开发者才会;
  - `aot/run_*.py`(测试夹具框架)与 `aot/native_link.py`(把发出的 LLVM IR 交给 clang 并链接出一个二进制)。

用 QLang 重写这些生成器会让整条工具链摆脱 Python。推迟:正常构建中没有任何东西依赖它们。

## 裸值:表示属于"值",装箱属于"使用点"

不变量(已定):每个节点只有一个*自然*表示,由编译期(`aot/types.ql`)算出并存放在节点上。任何消费者都不得改写它。需要装箱值的使用点*在那一处使用点*做强制转换(bitcast + pack,两条指令);能吃裸值的使用点直接用它。绝不因为有一个消费者要盒子就把节点降级为装箱:那会让这个值在每次使用处都装箱。装箱按使用计,不按值计。

表示:`"Number"`(裸 double)、`"Boolean"`(裸 i1)、`""`(装箱 `%ql_value`)。`emitValue(node) -> { reg, raw }` 返回自然表示,不接受 `want` 参数。

规则,自底向上地算在分析的第二遍里(第二遍已经能看到第一遍收集的全部写入,所以 `runtimeTypeFree` 是可靠的 —— `inferTypes` 会跑两遍 `inferStmts`):

  - `Number` 字面量        -> `"Number"`(零指令:`f64lit`)
  - `Identifier`            -> 被解析到的那个绑定的表示;需要一条与 `typeScopes` 平行的表示作用域栈,这样遮蔽与闭包捕获才能正确
  - `UnaryOp` `!`           -> 操作数为 `"Boolean"` 时为 `"Boolean"`
  - 算术 `+ - * & | ^`      -> 两侧都是 `"Number"` 时为 `"Number"`
  - 比较                    -> 两侧都是 `"Number"` 时为 `"Boolean"`
  - 其余                    -> `""`

能吃裸值的使用点(直接取裸值,零成本):裸算术与裸比较、`if`/`while` 条件、写入解箱槽位,以及被调者表示签名静态已知时的实参与返回值。只能吃装箱值的使用点(在此处做强制转换,且仅在目标静态未知时):对象与数组的写入、被调者未知时的实参与返回、字符串运算。

这取代并否决了本分支上试过的试算版生成端:`emitMayBeRaw` 加 emit-then-fall-back 量测到 897 个 `fcmp` 只有 2 个裸命中,并在每次失败尝试时重新发射操作数(所以行数只涨不跌)。表示只算一次之后,一个节点恰好只有一条发射路径,于是重复发射与失败尝试在结构上不可能 —— 行数也变得单调,而这正是验收指标所需要的。

槽位政策(域,与上述无关):可解箱 = 内建标量注解、`runtimeTypeFree`、函数局部;模块根绑定永不解决,因为扩展桥会把帧 memcpy 给解释器(使用点未知)。

顺序:(1) 分析层算出 `staticRep` 加表示作用域栈 —— 不动代码生成,先按表示统计节点数来验证;(2) 生成端读取、算术、比较与条件都照 `staticRep` 走;(3) 对解箱槽位与注解参数做裸写入;(4) 只在真正未知的使用点装箱。

验收:裸比较命中数从 2 涨到数百,IR 跌破 215919 行的 t20 基线,探针输出不变(20/20/21/4),解释器 53/53,自举门禁 47/47。先报命中数,再报行数 —— 否则一个从未执行的改动会被读成没有收益。

分支:`unboxed-values`,已验证的第一刀停在 `8f98254`(仅契约,IR 逐字节不变);工作留在那里,并在合入 `dancing-with-dragon` 之前停止。已被取代的试算补丁:`cut2-raw-values`、`cut2-raw-arith-and-cmp`、`cut2-D-rawboolean`、`arm2-only-whitelist`。
