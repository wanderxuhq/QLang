# QLang 的 `Result(T, E)` 类型 —— 设计提案（中文版）

状态：提案，待评审。本文中的内容尚未实现。

英文原版：[result-type-proposal.md](./result-type-proposal.md)

## 动机（实测）

- 现在**任何值都可能是 Error**，所以每个读/写点都要付一次"这是不是 Error？"的检查：
  把这些检查全部去掉，一个完整模块会缩小 **19.5%**（247,351 → 199,072 行）。
- 编译期不知道类型，逼得每个运算符都同时发出"专用路径 + 通用路径"：
  同一条语句，类型已知时 **21 行**，类型未知时 **62 行**。
- 根本缺陷正是你已经点明的那条：现在 `Number` 的真实含义是"**Number 或 Error**"，
  这就是 Java 的 `T or null` —— 类型变成了一句谎话，每个使用点都被迫处理那份额外状态。

## 关键观察：这件事比看上去小得多

现有实现里的三个事实，让 Rust 式 `Result` 变得很便宜：

1. **`?` 早就存在，而且就是那个语法糖。** `emitPropagateError` 所做的只是"把错误写进
   返回槽 + 跳到 epilogue"（顶层则走 `__exit_error`）—— **没有任何栈展开，传播是一个
   静态分支** ✓。这正是"是 Err 就从当前函数返回它，否则取出值"。
2. **运行时的表示本来就是一个"未装箱的联合"。** 一个 `%ql_value` 是 tag + payload：
   要么是普通值，要么是 tag 8 加那个 Error 对象 ✓。所以 `Ok(T)` **就是**那个普通的 `T`，
   `Err(E)` **就是**现有的错误对象 ✓ —— **没有包装、没有分配、没有新的运行时机制** ✗。
3. **类型值就是 `{check: 函数}`。** `let Number = { check: __pred_number };`、
   `std.Type.make(f)` —— 类型就是普通对象；`Array(Number)`、`Object({a: Number})`
   都是库层面的构造器 ✓。所以 `Result(T)` 只是一个 **QLang 函数返回的 `{check: …}` 对象** ✓，
   **不需要改动类型系统内核** ✓。

一句话：这件事的本质是**类型层面**的改动（声明、检查、以及编译器可以假设什么 ✓），
**不是表示层面的改动** ✓。

## 设计

1. **表示：不变。** `Ok(v)` 就是 `v`；`Err(e)` 就是那个错误值。
   因此 `Result(T)` 天然就是未装箱的 `%ql_value` —— **根本没有东西需要去装箱** ✓。
2. **类型本身：** `std.Result(T)`，作为标准库导出项、**用 QLang 写在
   `stdlib/result.ql`** ✓：一个用现有类型机制构造出的类型值，其 `check` 接受一个 `T`
   或一个错误 ✓。QLang 里的错误载体只有 Error 对象，所以错误侧固定为 `Error`；若将来
   出现第二种载体，再加双参的 `Result(T, E)` 也不迟。
   这需要先**放开库命名空间的限制** ✓：导出项不必是**模块对象** ✗，可以是任意值
   （函数、类型、标量 ✓）—— 于是类型构造器可以作为普通的 `std` 成员存在 ✓
   （那次崩溃与修复见 `docs/stdlib-capability-gaps.md` ✓）。
3. **`?` 的语义：不变。** `v?` 现在的含义已经是"若 v 是 Error 就把它从当前函数返回，
   否则产出 v"—— 在这套表示上，这就是 Result 的传播 ✓。改变的只是它的**类型**：
   `?` 之后的值是一个 `T` ✓。
4. **类型纪律**（这才是真正的改动）：
   - 可能失败的绑定/返回值声明为 `Result(T)` ✓，由现有的检查机制强制 ✓；
   - 带 `Number` 类型信息的绑定**永远不可能**装着 Error ✓（因为"带类型的绑定只持有它的类型"
     已经成立：检查失败即传播 ✓）；
   - 要把 `Result(T)` **当作** `T` 使用，必须写 `?` ✓ —— 也就是说失败必须在**边界**上被承认 ✓，
     这和 Rust 把失败放在边界是同一个位置 ✓。

## 编译器能得到什么

- 已知是 `Result(T)` 的绑定：它的 Ok 载荷就是 `T` ✓，而 `?` 之后就是纯粹的 `T` ✓ ——
  于是运算符路径与表示都可以**特化** ✓（带类型的 `x + 1` 实测目标：约 60 行 → **2–3 行**；
  对照今天"类型静态已知"的 21 行 ✓）。
- **没有被声明为 `Result` 的值不可能是一个 Error** ✓ —— 于是它那些"每值检查"变成**可证死代码** ✓：
  这就是那 19.5%，而且现在的删除是有**类型依据**的 ✓，不是盲删 ✓。

## 迁移：注解优先

- **A. 关掉自动传染** ✓ —— 两种模型都需要它作为前提。已开始：读路径不再附加检查
  （`contagion-off` 分支，**−9.8%** ✓）。拦路的问题：**解释器本身是 QLang 写的**，
  它的表达式处理把"运算产生的错误"当成**退出**（`isExiting(right) → return right` ✓），
  于是两个引擎不一致 ✓ —— 这就是步骤 A 剩下要做的**解释器侧对齐** ✓。
- **B. 加入 `std.Result`** ✓ —— 一个 QLang 类型构造器，外加把 `?` 作为其语法糖写进文档 ✓。很小 ✓。
- **C. 给标准库的接口加类型信息** ✓ —— 那些可能失败的成员标上 `Result(T)` ✓。
  注意这是**声明级的改动** ✓：一个"失败时返回错误值"的库函数**本来就是 Err 分支** ✓，
  **不需要重写函数体** ✗ —— 迁移量因此小得多 ✓。
- **D. 编译器特化** ✓ —— 像识别 `Number` 那样识别 `Result`（作用域感知的名字匹配 ✓），
  穿过它做特化 ✓，并删掉因此变成死代码的检查 ✓。
- **E. 可选的后续** —— 双参/结构化变体；把解释器自身的错误流也收紧到与编译器一致 ✓。

## 验证

- 现有套件，尤其是**位置/trace** 相关的那几套（`t38`、`t40`、source-context ✓）——
  它们对错误诊断最敏感 ✓。
- **自举不动点**（stage2 与 stage3 的 IR 一致 ✓）以及**两个引擎逐 fixture 行为一致** ✓。
- 新 fixture：`Result(Number)` 接受 Number 与 Error、拒绝 String ✓；`?` 穿过一次调用 ✓；
  以及一条**健全性**检查：错误不可能进入带 `Number` 类型信息的绑定 ✓。

## 待定问题

- 编译器对 `Result` 的**静态识别** ✓（特化需要它 ✓）—— 机制与内建类型名相同 ✓，
  但**不得特判库内部** ✓：识别应当是"对类型值的作用域感知名字匹配" ✓。
- **未注解的代码保持现有行为** ✓（保守回退 ✓），所以这次改动是**增量式**的 ✓。
- `E` 是否需要是 `Error` 以外的东西 ✓。
- 解释器里的 `isExiting`/`propagate` 记账必须继续服务 `return` 与 `?` ✓，
  但**不能再把"运算产生的错误"当作退出** ✓。
